# Preserve offline note edits across lifecycle changes

Offline edits may reach the server after another device has edited, locked, archived, trashed, or permanently deleted the original note. Keep the server's version and lifecycle state authoritative while preserving locally saved writing: this avoids silently losing an edit or undoing a deliberate action on another device, at the cost of a separate note for the user to review.

## Decision

- Show **Saved to device** after a local save and **Synced** only after server confirmation. A definite sync failure keeps the edit locally and shows its cause. Signing back in to the same account preserves the cache. Explicit logout offers sync or an explicit discard choice before clearing it; switching accounts requires that logout.
- If concurrent edits, a server lock, or a remote Archive or Trash action prevents applying an offline edit, keep the original's server state and preserve the offline title, body, and tags in a separate recovered copy. Do not automatically copy pinning, locking, or sharing. Do not alter the copy's title to indicate a conflict. Show its specific reason, a link to the original when available, and a **Needs review** marker across devices until the user explicitly clears it. A reviewed copy remains an editable note with its reason available. The sync indicator can say **Synced** while also reporting copies that need review.
- An offline Archive action applies a pending edit before archiving the original. If the server rejects the edit, preserve it as a recovered copy; if a lock rejects Archive, leave the original locked and unarchived and show a persistent failure notice. An offline Trash action on an existing note moves the server original to Trash and preserves a pending edit in a recovered copy. Confirm the copy before completing the removal; retries must not create duplicate copies. A note created and trashed entirely offline stays in local Trash until it can be created and trashed on the server.
- A lock blocks editing, Archive, and Trash until the server confirms an unlock. Rejected queued actions return the note to the correct list and remain visible until acknowledged. Archived notes remain eligible for automatic locking; trashed notes do not.
- Archive and Trash show cached notes offline as a clearly partial view, and queue restore or unarchive actions. The action that removes a note from Archive is labelled **Move to Trash**. Restoring from Trash preserves the note's archived status. Trash retains notes for seven days; permanent deletion and Empty Trash require a connection. If the server permanently deleted an original before a queued restore or edit reaches it, retain any locally saved content and offer **Save as new note** explicitly; never recreate the original automatically. A recovered copy remains available if its original is permanently deleted, with the unavailable original shown as such rather than a broken link.

## Consequences

The app must keep pending local work until the server confirms its intended outcome or the user explicitly discards it. Creating a recovered copy and completing a queued removal must be retry safe. A separate review state is required; a successful upload does not imply that the user has resolved the reason for the copy.
